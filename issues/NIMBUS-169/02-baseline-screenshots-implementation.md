## Solution Design

Per scope.md, cover 6 key flows × 8 locales × 2 viewports = 96 screenshot combinations: home, PLP
(product listing), PDP (product detail), cart, checkout, account pages. Each flow gets its own
spec file using Playwright's `toHaveScreenshot()`, run automatically across all 16
locale/viewport projects defined in Task 01's config (no per-locale duplication of spec code
needed — Playwright's project matrix handles that).

Baseline screenshots are generated once (`pnpm test:visual:update`) and committed to the repo
under Playwright's default `__snapshots__`/`-snapshots` directory convention — these become the
regression baseline for future runs.

import { expect, test } from '@playwright/test'

test('home page renders correctly', async ({ page }, testInfo) => {
  const countryCode = testInfo.project.name.split('-')[0]
  await page.goto(`/${countryCode}`)
  await expect(page).toHaveScreenshot(`home-${testInfo.project.name}.png`, {

## Test Cases

### TC-1: Baseline generation succeeds for all 6 flows × 16 projects
- **Given:** a running dev server and seeded backend
- **When:** `pnpm test:visual:update` runs
- **Then:** 96 baseline PNG snapshots are generated with no errors (page not found, timeout, etc.)

### TC-2: Re-running against the same code produces no diffs
- **Given:** the freshly-generated baselines from TC-1
- **When:** `pnpm test:visual` runs again immediately (no code changes)
- **Then:** all 96 comparisons pass (0 diff) — confirms the suite isn't flaky/non-deterministic by
  default (watch for animation/timing-based flakiness; disable CSS animations in test mode if
  needed via Playwright's `use.reducedMotion: 'reduce'` or similar)

### TC-3: A deliberate layout change is caught
- **Given:** the baselines from TC-1
- **When:** a CSS change is deliberately introduced (e.g. temporarily widen a container) and the
  suite runs again
- **Then:** the affected screenshots fail the comparison, confirming the suite actually detects
  regressions (this is a manual verification step during implementation, not a permanent test)

## Implementation Steps

1. Confirm a stable, real seeded product handle to use for PDP/cart/checkout specs (see
   `initial-data-seed.ts` for seeded product titles — derive their handles, e.g. via a slugified
   title or by querying `/store/products` once against a seeded instance).
2. Write all 6 flow spec files following the pattern above, each with flow-appropriate setup.
3. Run `pnpm test:visual:update` to generate and commit the 96 baseline screenshots.
4. Run `pnpm test:visual` immediately after (TC-2) to confirm zero flakiness before committing.
5. Perform the deliberate-regression check (TC-3) once, then revert the deliberate change.
6. Run `pnpm lint` (spec files are still TypeScript, lint applies).

## Risks

- **96 committed PNG snapshots** add meaningful repo size — acceptable for a one-time baseline,
  but flag to the user if binary-snapshot bloat becomes a concern (e.g. via Git LFS) as the suite
  grows over time with future re-baselining.
- Authenticated account-page screenshots need a stable, seeded test user/session — coordinate with
  whatever seed data already provides Customer/auth fixtures, or add one if none exists (check
  `initial-data-seed.ts` — it does not currently seed a customer/user).
