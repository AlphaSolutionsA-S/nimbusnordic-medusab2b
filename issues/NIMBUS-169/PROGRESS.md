  - **Task 04 (DONE) — critical finding:** Before triaging CSS breaks, opened a sample of German/French baseline screenshots to actually read the rendered text (the automated diff alone can't catch this, since a suite generated from the current app state is self-consistent even if that state is wrong). **Every non-English locale (da, sv, no, pl, it, fr, de) rendered the storefront entirely in English** — confirmed via raw `curl` (no browser/Playwright involved) against both `next dev` and a production build, across `/de/account`, `/de/products/...`, and others. The `messages/*.json` catalogs (NIMBUS-167) are correct and complete; they were simply never being loaded for non-English locales.
    - **Root cause:** `[countryCode]/layout.tsx` calls `setRequestLocale(countryCode)` before `getMessages()`, exactly per next-intl's documented pattern — but instrumenting `src/i18n/request.ts`'s `getRequestConfig` callback showed `requestLocale` resolving to `undefined` even on an *immediate* read-back within the same function call, in both dev and prod. Since this app deliberately doesn't use next-intl's own `[locale]`-segment middleware (locale is derived from the existing `/{countryCode}/` segment instead — see the comment history in `i18n/request.ts`), nothing was ever setting the `X-NEXT-INTL-LOCALE` header that next-intl's `requestLocale` falls back to reading when `setRequestLocale`'s value isn't available — which is next-intl's own documented mechanism for exactly this "custom locale resolution" scenario.
    - **Fix:** `middleware.ts` now sets `X-NEXT-INTL-LOCALE` from the URL's country code (via the existing `getLocaleForCountry`) on every successful request. `i18n/request.ts` now treats `requestLocale` as an already-resolved real locale (validated against `SUPPORTED_LOCALES`, defaulting to English otherwise) rather than re-running it through `getLocaleForCountry` — necessary because "da"/"sv" (locales) don't match "dk"/"se" (country codes) and would otherwise silently fall back to English even with the fix. Updated `i18n/request.test.ts`'s TC-2/TC-3 to reflect this corrected contract. `setRequestLocale` is left in place in the layout as a harmless defensive fallback.
    - **Verified the fix directly via curl** (bypassing Playwright) across `/de`, `/fr`, `/pl`, `/dk`, `/se`, `/gb` — all render correctly localized UI text (including the two locales, Danish and Swedish, whose locale code differs from their country code, which would have silently broken again with a naive fix). `pnpm lint`, `pnpm test` (134/134 suites), and `pnpm build` all pass.
    - **This also invalidated Task 02's original 96 baselines** (screenshots of the English-only bug state) — regenerated all 96 against the now-correctly-localized content and reran the full 144-test suite twice for stability (only expected transient contention flakiness, consistent with Task 02's findings).
    - **Two more test-only bugs found and fixed while regenerating baselines:** `addTestProductToCart` (cart/checkout specs) waited on the add-to-cart button's re-enabled state, but the button re-enables immediately after emitting an event onto an event bus (`product-variants-table/index.tsx`'s `handleAddToCart`) — the actual async `addToCartBulk` server action (in `cart-context.tsx`) fires afterward. A `page.goto` right after could abort that request mid-flight, so the previously-committed cart/checkout baselines were silently screenshotting an **empty cart** and a **404 not-found page** respectively, not the intended states. Fixed by waiting for the network to go idle before navigating, and both specs now assert `cart-item-subtotal` is visible to positively confirm the real state was captured.
    - **Visual triage of the (now genuinely localized) content:** manually reviewed German, French, and Polish screenshots (the longest-expansion languages) across both viewports and all 6 flows. **No CSS-level layout breaks found** — every heading/button/nav label wraps gracefully within its container (e.g. German's 4-line "Für einen schnelleren Checkout anmelden." heading, Polish's 4-line login heading). No baseline updates were needed for false positives, and no translated content was altered to mask an overflow (TC-2 of Task 04) — the fix was entirely in routing/locale-resolution code, not in any component's copy.
  - **Minor, out-of-scope finding (not fixed, flagged only):** `app/layout.tsx`'s `<html lang="en">` is hardcoded regardless of locale — a separate, smaller SEO/accessibility issue from the one just fixed (this one affects the `lang` attribute only, not visible UI text), and fixing it would require making the root layout locale-aware, which has broader static-rendering implications. Worth a follow-up.
