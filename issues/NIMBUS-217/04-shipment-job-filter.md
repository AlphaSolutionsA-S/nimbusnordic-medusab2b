# 04: Shipment job skips and closes switched-off companies
**App:** backend · **Layer:** L0 (tracking close-reason enum), L3 steps, L5 check schedule, Admin UI label · **Issue:** NIMBUS-221 · **Depends on:** 03

**Goal:** Discovery never tracks shipments of switched-off companies (cursor still advances, no back-fill); the check run closes each due open row of a switched-off or missing company with close reason `company_not_enabled` without reading it from Business Central.
**Files / areas:** `src/modules/order-ingestion/models/shipment-tracking.ts` (+ generated migration), `src/workflows/shipment-notice/steps/{scan-shipment-windows,prepare-shipment-checks,check-shipments}.ts`, `src/workflows/shipment-notice/utils/shipment-check-schedule.ts`, `src/admin/hooks/api/shipment-tracking.tsx`, `src/admin/routes/shipment-tracking/page.tsx`.
**Seam contracts:** close-reason wire value `company_not_enabled`; the rule from task 03 is the only place that decides "enabled". Each due check carries whether its company is enabled, read in the preparation step with one companies query for the batch. Business Central request count per run unchanged (N4).
**Test intent:**
- Unit: the check schedule closes with `company_not_enabled` for the new outcome, keeping `attempts`/`last_error` semantics like `superseded`.
- Integration `discover-shipments.spec.ts`: a header of a switched-off company is not tracked and the cursor passes it; switching the company on later does not track it (R7); an enabled company's header is tracked as today.
- Integration `check-shipments.spec.ts`: a due open row of a switched-off company closes `company_not_enabled` with no Business Central read for it and its stored notices kept; an enabled company's row in the same batch is checked as today; a closed `company_not_enabled` row stays closed after switching on and another run (R9).
- Admin test: the overview shows a label for the new close reason.
**Done when:** tests pass; migration generated (check constraint re-created with the new value); existing shipment specs switch their companies on and stay green; lint, typecheck at or below baseline.
**Verify after deploy:** `shipment_tracking` rows of a test company left switched off show `close_reason = 'company_not_enabled'` after the next due run; rows of a switched-on API company stay open.
**Also update:** `integration-tests/http/shipment-notice/{discover-shipments,check-shipments,poll-shipment-notices}.spec.ts`, `src/workflows/shipment-notice/__tests__/shipment-check-schedule.unit.spec.ts`, `src/modules/order-ingestion/__tests__/shipment-notice-storage.spec.ts` (only if it enumerates close reasons), `src/admin/routes/shipment-tracking/__tests__/page.test.tsx`, `integration-tests/http/admin/shipment-tracking.spec.ts` (reason union in its seed helper).

## Deviations

- **Blocking: migration not generated.** `corepack pnpm --filter @b2b-starter/backend exec medusa db:generate orderIngestion` fails here (no PostgreSQL: `ECONNREFUSED`, run killed after the pool timeout). Not hand-written. Expected generated SQL: `alter table if exists "shipment_tracking" drop constraint if exists "shipment_tracking_close_reason_check";` then `alter table if exists "shipment_tracking" add constraint "shipment_tracking_close_reason_check" check ("close_reason" in ('cancelled', 'window_ended', 'superseded', 'gave_up', 'company_not_enabled'));` (down: the same with the four old values), plus the updated `.snapshot-order-ingestion.json`. Until it is generated, the new close reason violates the check constraint in a real database, and every integration test that closes a row with it fails.
- **Resolved (fix 01, 2026-10-23):** generated `Migration20261023110454.ts` with exactly the SQL above (drop and re-create the check with `company_not_enabled`; down restores the four old values; nothing else) and the updated `.snapshot-order-ingestion.json`; `medusa db:migrate` applied it on the throwaway database.
- **Integration and contract tests written but NOT run** (no database in this environment): `discover-shipments.spec.ts`, `check-shipments.spec.ts`, `poll-shipment-notices.spec.ts`, `admin/shipment-tracking.spec.ts`. They typecheck.
- **Open question (R7 edge):** discovery has a lead scan and a trail scan that re-reads headers up to `SHIPMENT_TRAIL_LAG_MS` (30 min) behind it. If a company is switched on in the window between the lead scan passing a header and the trail scan re-reading it, the trail scan tracks that header. "Never back-filled" therefore holds once both cursors have passed the header (at most ~45 min after its last change). Closing that gap needs stored state per skipped header; not done. The R7 test puts the header behind both scan bounds so it asserts the guaranteed behaviour.
- Added case: a due row whose company no longer exists closes `company_not_enabled` without a BC read (plan flow D2 says "or no longer exists"; the test intent did not list it).
- Added case: the Admin overview contract test seeds a `company_not_enabled` row (count 5 → 6) to show the route returns the new reason.
- A `company_not_enabled` close sets `last_checked_at` to the run's time and counts in the run's `checked`, exactly like `superseded` (test intent: "like superseded"), although no BC read happened. No new run-result counter.
- `check-shipments.spec.ts` used a non-existent company id (`comp_shipment_checks`) for all rows; with this task every such row would close `company_not_enabled`, so the spec now seeds an enabled company in `beforeEach` and tracks rows under it.
- `discover-shipments.spec.ts` and `poll-shipment-notices.spec.ts` now seed companies through `createApiCustomerCompany` (switched on) instead of a bare `createCompanies`; the poll spec's company name changes from "Shipment Poll Co" to "Notice Co C-100" (nothing asserts it).
- `shipment-notice-storage.spec.ts` unchanged: it does not enumerate close reasons.
