# 05: Preserve formatting and SEO with rollout verification
**App:** Storefront / documentation · **Layer:** S1, S3; integration verification · **Depends on:** 03, 04

**Goal:** Complete dynamic-language formatting and collision-free alternate links, prove the ninth-language journey and document rollout/failure limits.
**Files / areas:** apps/storefront/src/lib/{i18n/formatting-locale.ts,seo/locale-alternates.ts}; app/[countryCode]/(main)/{products,collections,categories}/ metadata; src/__tests__/app/page-metadata-locale.test.ts and helper tests; e2e/visual/{region-switcher,locale-links}.functional.spec.ts; docs/architecture/country-languages.md (new); src/lib/i18n/README.md; relevant ai/architecture and skill project.md entries.
**Seam contracts:** buildLocaleAlternates accepts 04 snapshot plus path, configured countries only; key canonical language/script with URL country region, preserve variants, omit extensions, never overwrite same-language countries. getFormattingLocale(string) retains current eight outputs, handles valid new tags including script/region forms, and safely falls back for malformed input; currency remains supplied by Region/commercial data.
**Test intent:**
- Jest: preserve eight formatting tags, nl/pt-BR/zh-Hant accepted, malformed tags safe, no double region or extension-bearing hreflang; two English countries retain both URLs and removed countries disappear.
- Metadata specs: products/collections/categories take same request publication as layout; assert locale and every alternate URL/key at caller depth.
- Playwright functional/integration: bootstrap fixture, create/activate ninth language, Admin assigns a configured country, fresh page language/text/formatting/switcher/metadata agree, same-language country links survive; capture response/rendered artifacts.
- Browser security case: logged-in session cannot mutate mapping from foreign-origin form or fetch; test actual cookies/preflight and unchanged stored assignment, not only mocked requests.
**Done when:** Appropriate changed tests plus final integration/browser checks pass or only independently recorded baselines remain; current docs describe every changed rule and ordered rollout. Reload storefront SEO and design references before changes; no cosmetic storefront redesign.
**Verify after deploy:** Record singleton assignments/version, GET /store/country-languages country/locale/source and rendered language/hreflang on the same configured nl test-country page, after a real Admin save; tests alone do not prove rollout.
**Also update:** __tests__/lib/{seo/locale-alternates,i18n/formatting-locale}.test.ts; named metadata/browser specs; lib/i18n/README.md adding-language and formatting sections; ai/architecture/{decisions,data-ownership}.md ownership now maintained by01, remaining current rule wording and relevant storefront skill project.md; run ai:check for ai edits. Existing docs/architecture has no locale document to amend.

## Deviations

- `getFormattingLocale`: a structurally valid tag outside the original eight (for example `xx`) now returns the tag itself, no longer `en-GB` (plan decision: valid tags use Intl's fallback); the old `xx` fallback case became malformed-tag cases (`""`, `en_GB`, `en-`, `../en`, `en GB`, 65 chars, `__proto__`, `constructor`).
- hreflang keys of the eight legacy countries change from the bare language (`da`) to language plus URL country (`da-DK`), as the plan's alternate-link decision requires; the three per-page metadata tests now assert `languages["da-DK"]` and mock the request loader with the legacy snapshot.
- Removed `SUPPORTED_LOCALES`, `Locale` and `getLocaleForCountry` (branch notes 04). Their test "keeps the legacy lookup for consumers not yet on the request snapshot" was removed with the function (the lookup is covered by "keeps the approved legacy map as a full snapshot marked legacy"); the `SUPPORTED_LOCALES` coverage test now asserts the legacy map's eight languages directly.
- Playwright: the journey, the browser security case and the switcher label check were written but not run. No backend was running on :9000, no Admin credentials are known to the worker, and the journey changes backend data (a region country, a ninth language, an assignment) that the human's local dev database should not get without a go-ahead. The specs skip with an explicit reason unless `E2E_ADMIN_EMAIL`, `E2E_ADMIN_PASSWORD` and `NEXT_PUBLIC_MEDUSA_PUBLISHABLE_KEY` are set; they compile (`playwright test --list`, storefront `tsc`).
- The browser security case lives in `locale-links.functional.spec.ts` (it shares the journey's fixture); a new helper `e2e/visual/country-language-fixture.ts` holds the fixture. Its restore cannot delete an explicit key (no API for it): it reassigns the previous or default language explicitly.
- Added a `decisions.md` row for the formatting-tag and hreflang-key helpers; also updated the stale Tier 0 `layers.md` S2 list, `boundaries.md` `bound-sf-server-only` and `ai/skills/nextjs-data-layer/project.md` for the `server-only` loader `lib/data/country-languages.ts`. `ai:check --fix` regenerated `AGENTS.md` and `.github/copilot-instructions.md`, which raises the pre-existing `AGENTS.md` size overrun to 33,861 bytes.
- Browser security case (rework): SameSite is asserted from the raw `Set-Cookie` that `loginAdmin` now returns, not from `context.cookies()` (which may report a missing attribute as `Lax`). Medusa sets `SameSite=Lax; Secure` only for a production or staging NODE_ENV and no SameSite otherwise, so the expectation follows the new optional `E2E_BACKEND_NODE_ENV` (default `development`): production-like expects `SameSite=Lax; Secure` and a 401 for the foreign form (cookie withheld); otherwise it expects no SameSite attribute and accepts 401 or 415 for the foreign form (fix brief 03: the real run against a development backend got 401, because this Chromium withheld the API-context login's cookie from the cross-site form POST; a browser that sends a cookie younger than two minutes on a top-level cross-site POST gets 415 from the strict-JSON check). The report attaches which status happened; the unchanged version and assignments are checked either way.
- Region-switcher locator (rework): the main layout renders `data-testid="region-switcher"` in the header (`modules/layout/templates/nav/index.tsx`) and the footer (`modules/layout/templates/footer/index.tsx`), so the specs use the header's (`locator('header').getByTestId(...)`, the only `<header>` in the storefront). Pre-existing: the test at HEAD "region switcher navigates to the selected region homepage" had the same strict-mode violation (the footer switcher landed in develop after that spec was written); fixed with the same one-line scoping since it is in the file this task changes.
- Added an environment section to `e2e/visual/README.md`. Stale and not fixed (outside this task): the same README says `webServer` runs `pnpm dev`, while `playwright.config.ts` runs `pnpm build && pnpm start`.
