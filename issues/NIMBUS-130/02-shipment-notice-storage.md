# 02: Shipment notice storage
**App:** backend · **Layer:** L0–L1 (`orderIngestion` models and service) · **Depends on:** None

**Goal:** Add `shipment_notice`, `shipment_tracking` and the single-row `shipment_notice_state` (plan
section 5), with a generated migration. Also the service methods discovery, checks and the endpoint
use, including the store against an expected revision (plan flow D).
**Files / areas:** `apps/backend/src/modules/order-ingestion/{models,service.ts,migrations}`.
**Seam contracts:** method names are the worker's; the shapes are fixed.
- **Store a revision.**
  - Input: `bc_shipment_id`, `expected_revision` (0 if none), the copied order fields, numbers,
    dates, `bc_last_modified_at`, status, content hash, payload, the tracking schedule to apply.
  - Under the counter-row lock it returns `stored` (cursor, revision), `unchanged` (hash equals the
    latest) or `conflict` (latest ≠ expected). Only `stored` takes a cursor.
  - It updates `shipment_tracking.latest_revision` in the same transaction.
- **Tracking.**
  - Upsert from discovery: insert open; for an open row only move `next_check_at` earlier.
  - Select due rows: open, `next_check_at` ≤ now, oldest first, limit.
  - Reschedule: next due, attempts, last error code, last checked.
  - Close with a reason, setting `closed_at`.
  - List the rows closed `gave_up`, newest first, paged (task 11).
  - Reopen a `gave_up` row: `open`, `attempts` 0, due now, `reopened_at`/`reopened_by` set (task 11).
    Any other state is refused.
- **Poll state.** Read (null before the first run); initialize atomically; set a cursor; set the BC
  back-off.
- **Company listing.** `sequence` > after, or `created_at` ≥ since; ordered by `sequence`;
  `limit` + 1.
All database-touching methods follow `data-service-transaction`; raw SQL only on this module's tables.
**Test intent (module integration):**
- **Visibility order (F7):** writer A holds its transaction open after taking cursor N; writer B
  tries to store and blocks. An independent reader on its own connection sees neither N nor N+1.
  After A commits it sees N without N+1; after B, both, in paging order.
- Same content stored twice at once → one row, one cursor.
- **Stale worker (F1):** revision 2 `cancelled` committed, then a store with expected revision 1 and
  a positive snapshot → `conflict`, nothing inserted, counter unchanged.
- Changed hash with the right expected revision → revision N+1 with `previous_sequence`; equal hash
  → `unchanged`.
- Unique (`bc_shipment_id`, `revision`) rejects a direct duplicate insert.
- Two first-use initializations at once → one state row.
- The due selection respects order and limit and never returns closed rows; an upsert never moves a
  due time later.
- The company listing never returns another company's rows.
