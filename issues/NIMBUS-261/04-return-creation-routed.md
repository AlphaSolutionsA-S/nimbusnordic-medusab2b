# 04: Return creation routed per company
**App:** backend · **Layer:** L6 route, L4 workflow, L3 steps · **Depends on:** 02

**Goal:** A return is validated against the source order and created in the company's environment.
**Files / areas:** `api/store/bc-orders/[id]/returns/route.ts`, `workflows/business-central-return/workflows/create-bc-return.ts`, `workflows/business-central-return/steps/{prepare,submit}-bc-return.ts`.
**Seam contracts:** `PrepareBcReturnInput` gains `environment: BusinessCentralEnvironment`; the workflow passes it to both steps (submit input through `transform`). The route resolves customer number and environment with the task 02 workflow (`{ customerId }`). Request id rule, validation and error mapping unchanged.
**Test intent:**
- Integration (same spec as task 03 or a sibling): a `NO` company's `POST /store/bc-orders/:id/returns` reads the order with `"NO"` and creates the return with `"NO"`; a `DK` company with `"DK"`.
- Negative: the order is not found in the company's environment (module returns `null` for that environment) → 404 "Order not found." and `createReturnFromSalesOrder` not called.
- Existing answers kept: invalid line → 400; ambiguous outcome → 503.
**Done when:** both steps receive the environment from the workflow input only, and typecheck shows no new errors.
**Verify after deploy:** after the customer-portal extension is deployed to TestNO (it is not yet; plan section 10), a test return created by a Norwegian test company's user appears as a sales return order in TestNO, not TestDK. Until then the create fails for NO companies with the existing 500 answer.
**Also update:** none found (no existing spec covers the return route; `security-boundaries.spec.ts` has no return-create case).

## Deviations

- **Error mapping made effective (behaviour change, needs a human look).** The route mapped failures with `instanceof MedusaError` / `instanceof BusinessCentralAmbiguousOutcomeError`, but a failed workflow rejects with the serialised error (verified: a probe running `createBcReturnWorkflow` with a fake BC module got a plain object, `instanceof` false for both, `name`/`type`/`__isMedusaError` present; source `@medusajs/orchestration` `transaction-orchestrator.js` `setStepFailure` → `serializeError`). So every failure answered 500 before this task, and the test intent's 404/400/503 could not pass. The route now reads the serialised fields: `name === "BusinessCentralAmbiguousOutcomeError"` → 503; `MedusaError.isMedusaError` + `type` NOT_FOUND → 404 "Order not found."; `name === BC_RETURN_VALIDATION_ERROR` → 400 with its message. Statuses and messages are the ones the route already declared.
- **400 narrowed to the return's own line validation (review rework).** Every other `INVALID_DATA` (BC configuration errors from `environment-config.ts`, `getClientCredentials`, and BC rejecting the return action with "The return request could not be accepted…") answers the logged generic 500, so no setting name or credential format reaches the shopper (CWE-209). To recognise the validation errors after serialisation, the prepare step now throws them through `returnValidationError()`, a `MedusaError` `INVALID_DATA` with `name = BC_RETURN_VALIDATION_ERROR` (`"BcReturnValidationError"`), exported from `prepare-bc-return.ts` and re-exported from `create-bc-return.ts` so the route imports only the workflow file. Messages unchanged. BC's "could not be accepted" rejection is deliberately not shopper-facing (it would need the BC service to throw the named error).
- **Baseline cleared.** The route no longer imports `modules/business-central/service.ts`, so its `bound-route-no-service` baseline entry was removed from `ai/architecture/boundaries.md` (regenerated `AGENTS.md`, `.github/copilot-instructions.md` via `pnpm ai:check --fix`), and the matching parenthetical in `ai/skills/medusa-infra-adapter/project.md` was rewritten.
- **Added test layer.** Besides the integration cases (not runnable locally), a route unit spec runs the real `createBcReturnWorkflow` in a real Medusa container with a fake BC module (only the account workflow is mocked, as in task 03), so the environment passing and the serialised error shape are proven locally.
- **Added cases:** an `environment` field in the body answers 400 without a BC call (strict body schema); no customer number → 400; the request id is the same in DK and NO (request id rule unchanged; this one passes before and after, a regression guard); all three line-validation messages → 400; BC configuration, credential and rejection `INVALID_DATA` errors → generic 500 with no `BUSINESS_CENTRAL` text in the body (unit), and a NO configuration error → generic 500 (integration).

## Done-when evidence

- Both steps receive the environment from the workflow input only: `prepareBcReturnStep` reads `input.environment` (workflow input passed straight through), `submitBcReturnStep` gets it from `transform({ input, prepared })` in `create-bc-return.ts`; proven by `src/api/store/bc-orders/__tests__/create-return-route.unit.spec.ts` "reads the source order and creates the return in the company's environment (NO)" / "(DK)" (`getOrder` and `createReturnFromSalesOrder` called with the account's environment), and by `integration-tests/http/business-central/store-bc-reads.spec.ts` "creating a return › reads the order and creates the return in NO|DK …" (written, not run locally: plan section 2 item 3).
- NO company → `"NO"`, DK company → `"DK"`: same tests as above.
- Order not found in the company's environment → 404 "Order not found.", `createReturnFromSalesOrder` not called: unit "answers 404 without creating a return when the order is not in the company's environment"; integration test of the same name.
- Existing answers kept: invalid line → 400 (unit "answers 400 with the validation message for …" ×3; integration "answers 400 for a line that cannot be returned"), ambiguous → 503 (unit and integration "answers 503 when Business Central's outcome is unknown"), other failures → 500 generic with a detail-free log line (unit "answers 500 without details …"; unit "answers the generic 500 for an invalid-data error from …" ×3; integration "answers the generic 500 without the setting's name for a Business Central configuration error"), no customer number → 400 (unit and integration).
- After-deploy note ("until then the create fails for NO companies with the existing 500"): holds again, since BC's rejection and configuration errors now answer the generic 500.
- Typecheck shows no new errors: `apps/backend/node_modules/.bin/tsc --noEmit -p apps/backend` → 22 errors, all in `integration-tests`, baseline 22.
- Also update: none needed beyond the baseline entries listed under Deviations (no doc or existing spec describes this route; storefront `createBCReturn` only throws on non-2xx, unchanged).
